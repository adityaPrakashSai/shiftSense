# Design decisions log

One line per non-obvious choice (design doc 11.4 rule 9): date, decision, reason.

- 2026-10-28 · Python env and deps managed with `uv` (`uv.lock` committed) · fast, reproducible installs; Docker uses `uv sync --frozen`.
- 2026-10-28 · `LLM_MODE` defaults to `live` in code but `.env.example` sets `mock`, and `make setup` copies it to `.env` · deployed app is live by default; a fresh clone runs offline with no keys.
- 2026-10-28 · `/api/health` reports `db` as `ok` / `absent` / `error` and opens SQLite read-only · a health check must not create the database file.
- 2026-10-28 · `make test` also runs `ruff format --check` · keeps generated code tidy (3.3).
- 2026-10-28 · `reference/` is excluded from ruff and from `make test`; run it with `make reference` · it is spec code, not app code (reference/README.md).
- 2026-10-28 · The fixtures zip was unpacked at the repo root (`data/seed/`, `tests/fixtures/`, `reference/`) and the design doc lives at `docs/DESIGN.md` · matches CLAUDE.md.
- 2026-10-28 · `SolveInput` splits hard availability into `unavailable` (sick/emergency), `leave` and `night_exempt` instead of one set · each maps 1:1 to a hard group in 5.2, so constraint names (`leave:N04:d2`) and the leave credit for `CONTRACT_MIN` need no extra lookup.
- 2026-10-28 · `SolveInput.standby_allowed` (False in full runs) carries the `standby_off_roster` rule; `Pref` has an optional `shift` so one type serves day-off, wanted and avoided prefs; `NurseHistory` adds `mornings` for `FAIR_MORNINGS` · fields 4.3 implies but does not list.
- 2026-10-28 · Carry-in history lives in a `ward_history` table (one JSON row per ward) · 4.4 has no home for it; seeds only give totals over earlier periods, not per-period rows. Per-period fairness history (US-12) will come from published runs.
- 2026-10-28 · `Ward.priorities` holds the tier order · `GET /api/ward` returns it (10.1) and the P1 settings panel edits it per ward.
- 2026-10-28 · Contract scaling rounds to 6 decimals before floor/ceil; `max_nights` = ceil(per_month x days / 30) as in the reference solver (3 per 14 days, 7 for real_a's 31 days) · avoids float noise turning 11.0 into 12.
- 2026-10-28 · Fixed duties (`Nurse.fixed_duty`) become `Forcing("fixed_duty", ...)` except on the nurse's leave or whole-day unavailable days · real_a's ANS has GH leave on 2 and 20 Oct, which would otherwise contradict her G duty.
- 2026-10-28 · Default seed `data/seed/ward.json` is generated by `scripts/gen_ward.py` (deterministic); all 20 regular nurses are night-qualified and standby S04 (trainee) is not · 56 target nights with a cap of 3 per nurse needs at least 19 night-capable regular nurses; S04 gives the counterfactual test (11.3) its non-night-qualified trainee.
- 2026-10-28 · Supply/demand sanity test runs on the default and mini wards only · real_a's printed month has Σ min contract 462 against 339 target slots (three nurses on whole-month ML, one on study leave), so the bracket does not hold there by design.
- 2026-10-28 · Fixture doubt (not edited): real_a's ANS has `consecutive_days = 3` while `last_days` is `["-", "-", "-"]` · G duty is recorded as off in `last_days`; M2's carry-in rules should treat the ANS's run length as the source of truth or skip her, since G is outside coverage.
- 2026-10-28 · An empty database is migrated and seeded with `SEED` at app startup; `make seed` deletes and recreates it · matches 11.1 ("seed if empty") and keeps reset simple.
- 2026-10-28 · M2 hard groups beyond the 5.2 tables: `max_nights:{n}` (5.2 text), `standby_off_roster:{n}:d{d}` (4.1), and `ans_general_duty:{n}:d{d}` (the ANS never works M/E/N; 4.1 roles) · each is a rule the design states in prose but does not list as a row. None is waivable.
- 2026-10-28 · The G (general duty) variable exists only on cells where G is forced (fixed duty) or published; the validator reports any other G as `general_duty_forced_only` · keeps G out of the search space for everyone else; G counts as worked for runs, `max_shifts` and hours, never for coverage, and counts as a day shift for `rest_after_night`.
- 2026-10-28 · Sliding-window names use the window's last day (`max_consecutive_days:N02:d0` = the run that day 0 would extend past K) and the validator reports each day a run exceeds K · model and validator agree name for name, which the `rule_check` test relies on.
- 2026-10-28 · Carry-in runs come from `consecutive_days` / `consecutive_nights`, while `rest_after_night` at d = -1 reads `last_shifts` · matches the reference solver and plan_check.py; for real_a's ANS (G recorded as "-") the run length is the source of truth.
- 2026-10-28 · `RosterModel(drop_groups=...)` removes whole hard groups; used only by tests to prove each rule bites (11.3) · waivers stay per-name via `SolveInput.waived`.
- 2026-10-28 · `solve()` runs the independent validator on every roster and raises if it reports anything · a disagreement between model and validator is a solver bug and must never reach a published run.
- 2026-10-28 · The solver CLI (`app/solver/cli.py`) is the one solver module that imports outside the package, and only `app.domain.seeds` and `app.planner.build_input` (pure, no database); seed parsing moved from `app/store/seed.py` to `app/domain/seeds.py` for that · the boundary test enforces it.
- 2026-10-28 · Write-up numbers, validator on real_a's printed October plan (M2): the planned grid breaks 0 hard rules at real_a's limit of 8 consecutive days; the hand-edited update breaks 2 (`min_cover:d12:N`, `min_cover:d13:N`: nights on 13-14 Oct at 2 against a floor of 3). At the synthetic limit of 6 the plan has 8 streaks of 7-8 working days (S4, N01, N08, N09, N11, N12, N14, N16; N12's includes 2 carry-in days from September), and 27 quick returns (E then M, soft) in both versions. All match reference/real_rosters/plan_check.py.
- 2026-10-28 · M2 solve times (coverage tier only, 8 workers): default ward 0.2 s (coverage 0, proven), mini ward 0.05 s (coverage 3, proven, equal to the golden vector), real_a 0.1 s (coverage 0, proven).
- 2026-10-28 · Soft weights follow the reference solver and the interview text where they differ from the 5.3 table: `CHANGED` 2 and `STANDBY_CALLED` 1 (standby first), `SINGLE_NIGHT` 3 · the golden vector (3/0/0/19/55) was computed with these; the table's 1s predate the 26-27 Oct interviews.
- 2026-10-28 · Doubt, not changed: `FAIR_NIGHTS` keeps nurses on an announced night break in the spread, as the reference solver does, although 5.3 says to leave them out · the golden fairness value 55 depends on it (mini README finding 6 lists exclusion as a suggestion). Revisit with the head nurse; changing it means regenerating mini_expected.json offline.
- 2026-10-28 · Fairness spreads also leave out nurses away for the whole period (every day leave or unavailable) · real_a has three nurses on month-long ML and one on study leave; with them in, every spread is pinned at 0 and the solver cannot balance anyone. No mini or default nurse is affected, so the golden vector is unchanged.
- 2026-10-28 · The ANS (role `ans`) is outside the contract, sequence and fairness terms as well as coverage · she works fixed G Mon-Sat; split-weekend and isolated-day penalties on her would be constant noise.
- 2026-10-28 · Stage `best` is stored as the tier's value in the final roster; the stage's own objective is kept as `stage_best` and in the `stage.done` event · an unproven tier can be improved by a later stage, and the invariant "cost rows sum to stage best" must hold for what is published.
- 2026-10-28 · `SOLVER_TOTAL_SECONDS` (default 9) caps one full solve; each stage gets min(stage limit, time left) · the default ward's requests and fairness stages each use their full 5 s, which made the total 10.4 s against G1's 10 s.
- 2026-10-28 · Dominance weights for `solve_weighted` come from each tier's worst case (sum of weight x upper bound of its terms); spread upper bounds use history + horizon length · tight bounds keep the multipliers small enough for CP-SAT.
- 2026-10-28 · Skipped tiers emit `stage.done` with `status: "skip"`; fairness spread terms name who sets the max and the min in their detail ("max 12 (N05), min 3 (N06)") · gives the explainer (M8) something to cite without recomputing.
- 2026-10-28 · Write-up numbers, M3 solves (8 workers): mini ward lexicographic 3/0/0/19/55, every tier proven, 2.2 s; dominance-weighted the same vector, proven, 1.0 s. Default ward baseline 9.0 s: coverage 0, stability 0, contract 0 proven; requests 15 (bound 8) and fairness 28 (bound 15) best found.
- 2026-10-28 · Write-up numbers, real_a re-solved from scratch (all tiers proven, 1.2 s) vs the printed October plan, over the 17 working ward nurses: per month, weekend shifts 3-8 printed vs 3-9 solved, mornings 4-11 vs 5-13, evenings 5-12 vs 2-11, nights 0-6 vs 4-7. (The design doc's "1-8 weekends, 3-13 mornings" counts a different nurse set; this one leaves out the ANS and the four nurses on leave all month.)
- 2026-10-28 · `run_full` is split into `start_full` (build input, insert the run as `solving`, log `run.started`; milliseconds) and `finish_full` (solve and write evidence; a worker thread) · `POST /api/runs` returns 202 with a run id that already exists, and the solve runs in the 2-thread executor under the ward's asyncio lock (3.4).
- 2026-10-28 · Every DecisionLog used by the API has a listener that pushes `{type: "event", seq}` to the ward's sockets through `hub.notify`, which is thread-safe (`run_coroutine_threadsafe`) · stage events come from CP-SAT worker threads.
- 2026-10-28 · The web client keeps an event cursor (`lastSeq`, started at the newest event via `GET /api/events?last=1`); while polling it turns new events into the same nudges the socket would send, and on every (re)connect it replays events missed since the cursor · found in the manual check: a run that finished while the socket was reconnecting was never shown; polling had stopped and the socket nudge had already gone out.
- 2026-10-28 · Polling starts exactly 10 s after the socket drops (its own timer), not at the next backoff retry · with 1/2/4/8 s backoff the first check would only come at 15 s.
- 2026-10-28 · Demo reset restores a snapshot of the freshly seeded database (`data/shiftsense.snapshot-{seed}.db`, made on first seed) table by table, keeping `llm_cache` · re-solving the default ward takes 9 s against US-9's 3 s; the restore takes well under 1 s.
- 2026-10-28 · `POST /api/dev/ws-off {seconds}` closes every socket and refuses new ones for a while · makes M4's "killing the socket falls back to polling" check repeatable.
- 2026-10-28 · Display codes (N/O, D/O, leave type) and daily totals are computed on the server (`planner/roster_view.py`, `planner/totals.py`) · one definition for the grid, the import checksum (7.8) and later the explainer.
- 2026-10-28 · `web/openapi.json` is committed and `src/api/schema.ts` is generated from it by openapi-typescript (`make api`); a test fails when the committed schema drifts from the app · keeps the TypeScript types honest without running the generator in CI.
- 2026-10-28 · Manual M4 checks (Chrome, default ward): Generate -> draft on screen with no refresh, timer 9.1 s (server 9.03 s) with every tier ticked off live; Publish in one tab -> the other tab shows the new published run within ~1 s; `ws-off` for 30 s -> "polling every 3 s" after 10 s, a run started during the outage appears as a draft through polling, Publish from the polling tab reaches the live tab, and the socket comes back afterwards.
- 2026-10-28 · `app/domain/edits.py` (the 7.2 `ConstraintEdit` models) landed in M5 instead of M6 · the mock intake parser and structured output need the schema; `Request.from_edit` and validation still come with the intake pipeline in M6.
- 2026-10-28 · Mock context convention: prompts put a JSON object between `<context>` and `</context>` (today, sender, nurses, message facts); the mock reads it, real models see it as part of the prompt · keeps the mock deterministic without a side channel; M6's intake prompt must follow it.
- 2026-10-28 · `llm_call` gained `reasoning` and `reasoning_tokens` columns, added to existing databases by a small column migration in `store/db.py` · 7.1 says the reasoning text and its token count are stored for the Log tab; the 4.4 table had no column for them.
- 2026-10-28 · Reasoning is taken from `reasoning_content` or `reasoning` on the message, plus any inline `<think>...</think>` in the content, and stripped from the answer before JSON parsing · which field Baseten uses is unknown until the smoke run; the smoke report records `reasoning_field`.
- 2026-10-28 · Retries are done by the provider, not the SDK (`max_retries=0`): 2 retries with 0.5 s / 1 s backoff on 429, 5xx, timeouts and connection errors; none on other 4xx; 30 s timeout · exact 7.1 semantics, testable without network.
- 2026-10-28 · A role switches to the JSON tool protocol after 2 native calls with malformed arguments (per process), or at once when the provider declares no native tools; both modes return the same ToolCall objects · 7.1 fallback; the switch is listed in `GET /api/llm/usage` (`json_protocol_roles`).
- 2026-10-28 · Prompt text lives in `app/llm/prompts/` even for the gateway's own instructions (`json_protocol.md`, `json_schema.md`) and the smoke prompts · rule 7 of 11.4; the cache key hashes the files of each role.
- 2026-10-28 · Prices in `app/llm/prices.toml` are PLACEHOLDERS ($0.50 / $2.00 per million tokens for Muse Spark Open on Baseten, $1 / $4 default), deliberately high so the spend cap errs safe · the real numbers must come from the providers' pricing pages (9.4); update the file and this line.
- 2026-10-28 · The app imports `data/llm_cache.jsonl` into the cache at startup (entries already present win) · a fresh clone can run `LLM_MODE=replay` with no keys (9.1, M11).
- 2026-10-28 · M5 smoke run against Baseten (`meta-models/muse-spark-open-1026`): strict `json_schema` response_format works (answer parsed first try, 3.7 s); native tool calls work (`get_shift` with correct N07 / date args, no JSON-protocol fallback needed); reasoning arrives in `reasoning_content` (~2k chars, 438 of 460 completion tokens are reasoning); second identical call through the gateway was a cache hit in 1 ms · answers Q3/Q4: Baseten caps stay `native_tools=True, json_schema=True`; budget for reasoning tokens dominating completion cost (about $0.001 per small call at placeholder prices).
- 2026-10-28 · Baseten's provider caps now say `json_schema=False`: intake uses `json_object` mode with the schema in the prompt, and the schema is always put in the prompt, strict or not · M6 probes with the real ConstraintEdit schema: strict decoding without the schema in the prompt returned `intent: greeting` (or `change_demand`) for a plain Hinglish sick call, because the model reasons about a format it cannot see and the grammar then forces the tokens; strict plus the schema in the prompt once ran to the 4000-token cap. `json_object` plus the schema parsed it correctly. - 2026-10-28 · Leave and swap requests from a nurse go to a new status `pending_approval` after the nurse confirms, and become `active` only when the charge nurse approves (Q7); the same requests sent by the charge nurse are active at once · Q7 default; a minimal approvals strip on the charge view stands in until the Alerts tab (M7).
- 2026-10-28 · `cancel_request` and `change_demand` are stored as requests of kind `cancel` / `demand` and status `applied` once confirmed (withdraw the referenced request; set the ward's target for each date and shift) · every parsed edit then has one audit row with its source message; `build_input` ignores these kinds.
- 2026-10-28 · `Request` gained `counterpart_dates`, `counterpart_shifts`, `target_total` and `ref_request_id` (and the `request` table four columns; `message` gained the parse and reply) · an approved swap becomes four forcings in `build_input` (each nurse takes the other's shift and is off on their own day); demand and cancel need their target.
- 2026-10-28 · One Confirm confirms every pending request parsed from the same message, and runs one solve · a message with two edits should not need two taps or two solves.
- 2026-10-28 · Nurses can only send requests for themselves; the charge nurse (sender id `charge`) can name any nurse · 7.3 does not say; this stops a nurse marking a colleague sick.
- 2026-10-28 · Intake accepts dates from today to today + 34 (the calendar in the prompt); leave may run past the roster period and is clipped by `build_input`. Demand changes must fall inside the current period · "dates inside the horizon" in 7.3 read as the intake window, since planned leave is usually requested for a later period (eval case "20 to 22 Nov").
- 2026-10-28 · Weekday rules in `intake.md`: a bare weekday is the next such day after today, "this X" is in the current Monday-Sunday week, "next X" / "agle X" in the following week, and a bare weekday equal to today's weekday is ambiguous · makes the 9.3 ambiguous case ("I can't come on Thursday" with two Thursdays in range) well defined. Written after the eval cases, so the eval does not test it blind.
- 2026-10-28 · Hindi replies are Roman-script Hindi, worded gender-neutrally (imperatives and passives) · nurses write Roman Hindi on WhatsApp; the templates must not assume the sender's gender.
- 2026-10-28 · Questions (intent `question`) get a templated acknowledgement until the explainer arrives in M8 (7.5) · keeps the reply kinds stable for the UI.
- 2026-10-28 · The eval runner does not check swap cells against the published roster (`check_roster=False`) · the seed baseline comes from a time-limited 8-worker solve and differs between runs, so the swap cases would be flaky; the check itself is unit-tested.
- 2026-10-28 · The cache stores system prompts as their sha256 in `request_json` · the key already covers them through `prompt_version`; the committed `data/llm_cache.jsonl` drops from 0.96 MB to 0.41 MB for 50 entries.
- 2026-10-28 · Replay mode works without provider keys: an unconfigured provider is replaced by a stand-in that knows only its name and model (enough for the cache key) · CI replays the intake suite with no secrets.

- 2026-10-28 · A re-solve rebuilds its input from the current ward and all active requests (plus the published roster as `previous`), instead of patching the published run's stored `input_json` with the one edit (6.2 step 1-2) · same result for a single edit, and it also picks up demand changes stored on the ward and every other request confirmed since.
- 2026-10-28 · Shifts already under way on today (6.1) are handled as: their nurses' cells frozen, and extra `unavailable` rows so nobody else can be added to a started shift · `frozen_cells` alone cannot stop an off nurse being put on a shift that began at 07:00.
